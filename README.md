# Scalable API Gateway

A FastAPI-based API gateway with JWT authentication, Redis response
caching, per-client rate limiting, and a simple circuit breaker, routing
requests to two mock backend services (`user`, `order`).

Pre-alpha: both backend services return static placeholder data.
Configuration is centralized and environment-driven (see below), but the
shipped defaults — including the JWT signing secret — are dev-only and
must be overridden for anything beyond local use; see
[`SECURITY.md`](SECURITY.md).

## Architecture

```
Client
  │
  ▼
FastAPI app (gateway/main.py)
  ├─ log_requests       (gateway/middleware/logging.py)
  ├─ rate_limiter        (gateway/middleware/rate_limit.py, in-process)
  ├─ jwt_auth             (gateway/middleware/auth.py)
  └─ cache_middleware     (gateway/middleware/cache.py, Redis-backed)
  │
  ▼
router.py — round-robin + circuit breaker (services/circuit_breaker.py)
  │
  ├─ user_service   (services/user_service.py)
  ├─ user_service_2 (services/user_service_2.py)  — second instance, load-balanced
  └─ order_service  (services/order_service.py)
```

The list above is the actual request execution order: `log_requests` →
`rate_limiter` → `jwt_auth` → `cache_middleware` → `router`. That order
is the *reverse* of how the middleware is registered in
`gateway/main.py` (a Starlette behavior — the last-registered middleware
runs first). Auth and rate limiting deliberately run before the cache so
neither can be bypassed by a cache hit.

Note: `rate_limiter` is a plain in-process counter (`request_log`, a
dict keyed by client IP) — it is not Redis-backed, and its state is not
shared across multiple gateway instances. Only response caching uses
Redis.

## Getting started

### Requirements

- Python 3.13 (matches the checked-in `venv`; not tested on other versions)
- Redis reachable at `localhost:6379`

### Run locally

```bash
python -m venv venv
source venv/bin/activate   # venv\Scripts\activate on Windows
pip install -r requirements.txt

# In separate terminals:
uvicorn gateway.main:app --port 8000
uvicorn services.user_service:app --port 8001
uvicorn services.order_service:app --port 8002
uvicorn services.user_service_2:app --port 8003
```

### Run with Docker Compose

```bash
docker compose up --build
```

Brings up Redis, the gateway, and all three mock services. By default
routing still resolves to `localhost:<port>` (see "Configuration"
below), so every service runs with `network_mode: host` rather than a
Docker bridge network — works on Linux; see the comment in
`docker-compose.yml` for the Docker Desktop caveat.

### Configuration

`gateway/config.py` is the single source of truth for every configurable
value (JWT secret/algorithm/expiry, Redis host/port/db, cache TTL, rate
limits, circuit breaker thresholds, demo credentials, backend service
URLs) — each is read from an environment variable at process start, with
a default that reproduces the app's original hardcoded behavior. Every
variable, its default, and which file consumes it is listed in
[`.env.example`](.env.example).

There's no `.env` autoloader (no `python-dotenv`) — copying
`.env.example` to `.env` alone has no effect. Export the values into the
actual process environment, or point `docker compose` at the file
(`docker compose --env-file .env up`).

The defaults are for local development only — `SECRET_KEY` and
`DEMO_ADMIN_PASSWORD` in particular must be overridden before this
gateway is exposed anywhere but a developer's machine.

### Local login

There is no database — `gateway/auth_store.py` provides an
`InMemoryUserStore` seeded with a single development user (bcrypt-hashed,
reset on every restart). The seeded username/password come from
`DEMO_ADMIN_USERNAME`/`DEMO_ADMIN_PASSWORD` (see `.env.example` for
defaults). It exists to unblock local development only and is not a real
user base.

## API

- `GET /` — health check
- `POST /login` — body `{"username": "...", "password": "..."}`;
  returns `{"access_token": "..."}` on success, `401` on invalid
  credentials, `422` on a malformed/missing body. See "Local login" above
  for how development credentials are provisioned.
- `{METHOD} /{service}/{path}` — proxied to the matching upstream service
  in `gateway/config.py` (`settings.routes`, overridable via
  `USER_SERVICE_URLS`/`ORDER_SERVICE_URLS`)

Full request/response schema: `/docs` (FastAPI's autogenerated Swagger
UI) when the gateway is running.

## Monitoring & Dashboard

The gateway includes lightweight, built-in operational monitoring and a dashboard to track system health in real-time.

- **`GET /admin/stats`** — Returns a structured JSON document representing the current state of the gateway:
  - Gateway status, version, and uptime
  - Request counters (total, successful, failed, blocked)
  - Cache performance metrics (hits, misses, hit ratio)
  - Per-service request distribution
  - Circuit breaker states (`CLOSED`, `OPEN`, `HALF-OPEN`)
- **`GET /dashboard`** — Serves a lightweight, vanilla HTML dashboard displaying the metrics. It auto-updates every 5 seconds.
- **`POST /admin/reset-stats`** — Resets all request and cache counters back to zero without restarting the application (does not reset uptime). Intended for development and testing only.

**Auth posture (intentional, for this project):** `/admin/stats`,
`/dashboard`, and `/admin/reset-stats` are development/observability
endpoints and are **intentionally unauthenticated** in the current
project — they're exempted from `jwt_auth` alongside `/`, `/docs`, and
`/login`. This is acceptable for a local/demo gateway but is **not**
appropriate for a production deployment: exposing `/admin/reset-stats`
publicly would let anyone wipe operational counters with no credential.
In a real deployment these routes should sit behind authentication
and/or network-level access controls (e.g. internal-only network,
reverse-proxy IP allowlist) before being exposed.

## Project layout

```
gateway/
  main.py               Entry point — app assembly, middleware wiring, /login, /admin/*, /dashboard
  config.py              Centralized environment-driven settings (single source of truth)
  router.py              Round-robin proxy + circuit breaker integration
  auth_store.py           In-memory demo credential store (bcrypt-hashed)
  middleware/             log_requests, rate_limiter, jwt_auth, cache_middleware
  monitoring/              Request/cache/circuit-breaker counters (gateway/monitoring/metrics.py)
  templates/               dashboard.html, served by GET /dashboard
  utils/                   Redis client
services/   Mock upstream services + circuit breaker
docker/     Supporting Docker assets (see docker/README.md)
docs/       Project documentation
tests/      Test suite (auth, config, middleware pipeline, monitoring)
assets/     Diagrams, images referenced from docs
```
